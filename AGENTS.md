# AGENTS.md — cow-indexer

Standalone multi-chain CoW Protocol indexer: per-chain EVM JSON-RPC (`eth_getLogs` + block headers) and the CoW partner-gateway API (`partners.cow.fi/<network>`,
gnosis = `xdai`, every other path = the chain key, `config/chains.yaml:18-106`) → one `cow-indexer continuous --chain all` process → the `cow_db` ClickHouse database
(repo default `cow_indexer`, `src/cow_indexer/config.py:104,151`). The one rule: exactly one `continuous` process per chain, ever; checkpoints and the enrichment queue
live in ClickHouse with no transactional lease. Module paths below are relative to `src/cow_indexer/`, everything else to the repo root.

## Where this runs (production)

GKE Autopilot, deployed by Terraform from the private deployments repository (gnosisdevops/infrastructure-gnosis-analytics, stack directory named after this app).
Production runs only the image entrypoint `cow-indexer` (`Dockerfile:19`) with explicit args (`deployment.tf` args, `cronjob.tf` `sh -c`). The image's default
`CMD ["continuous", "--chain", "all"]` (`Dockerfile:20`) makes a container started with NO args a second writer on every chain, so every Job template, `docker run` or
exec must pass the subcommand. Outside the image a bare `cow-indexer` prints help and exits (`cli.py:26-28`); only the image's CMD turns no-args into a writer.
LOCAL-ONLY, read by nothing in the cluster: `Makefile`, `docker-compose.yml`, `.env` / `.env.example`, `.claude/settings.local.json`. The CLI never reads `.env` (no dotenv
under `src/`; `from_env` uses `os.getenv` only, `config.py:144-164,217-252`), so `uv run` / `make` / pytest reach production only if the shell exports the variables. Compose
does read it, through `env_file` (`docker-compose.yml:13-15,22-24`) and `${...}` interpolation (`:2-7,21`). Assume any `.env` in a checkout is production-shaped (production
database, cloud host, `COW_CHAIN=all`): `docker compose up` then runs `migrate` and a second `continuous` writer on ALL chains, and `restart: unless-stopped` (`:31`)
resurrects it until `docker compose down`. A local `.claude/settings.local.json` (untracked) pre-allows `uv run *`, `docker compose *` and `docker exec *` (including `docker exec cow-indexer-indexer-1 sh -c ...`; `.claude/settings.local.json:4-7`), so any subcommand — `drain`, `purge-work`, `migrate` — runs without a prompt, inside a running local container too: never invoke them here.
Restart: the scan is kill-safe — each chain resumes at checkpoint+1 (`services/historical.py:52-54`). Enrichment is NOT free to kill: items leased at the kill stay `running`
until the 5-minute lease lapses (`storage/clickhouse.py:1042`), already charged one attempt at lease time (`:1019-1020`); only a batch abandoned at its own deadline is refunded
(`services/enrichment.py:101-105` → `storage/clickhouse.py:1052-1089`), so repeated restarts, such as a crash loop, can use up `COW_MAX_ATTEMPTS` with
nothing processed. The item is still re-leased (`lease_work` does not filter on attempts, `storage/clickhouse.py:1005-1006`) and can succeed, but its next failure dead-letters it with no
retry (`services/enrichment.py:179-180`, `services/backfill_orderbook.py:284-285`). The enqueue-dedup set is in-process (`config.py:121-133`, `storage/clickhouse.py:158`): expect a re-enqueue burst for the first minutes. A pod-name change with
restarts=0 is a rollout (any applied change to the pod template) or an eviction/preemption, never a crash; check the Deployment's revision before assuming eviction.

## What does not exist, or does not do what its name says

- `COW_CHAIN` is not read by the application (no reference under `src/`); only `docker-compose.yml:21` expands it. The production Deployment sets it, but the chain set comes from the container args.
- `README.md:126` says the modes "share the durable checkpoints, so they interleave safely". False for `backfill` beside `continuous` on one chain: both call `store.checkpoint()` on the same `(environment, chain_id, 'rpc')` key (`storage/clickhouse.py:591-607`, `services/historical.py:96-97`). Only `repair` is checkpoint-free. The public docs page's "Running modes" section repeats the same claim; it is wrong there too.
- `status` takes no `--chain` (`cli.py:352`); `repair` requires `--chain`, `--from-block`, `--to-block` with no defaults and rejects `all` (`cli.py:161-175`).
- Every command resolves `config/chains.yaml` relative to the working directory and derives `project_root` (where `migrations/`, `deployments/`, `abis/`, `export-schema/` are found) as that file's grandparent (`cli.py:31`, `config.py:255-257`). Run from the repo root or the image's `/app`, or pass an absolute `--config`.
- `purge-work`'s precondition — scheduled purge disabled and `continuous` paused (`cli.py:131-133`) — is not enforced by anything.
- `preflight` exits 0 when the CoW API is unreachable as long as RPC works (`services/preflight.py:83-85`); it is an RPC readiness gate, not an API one.
- `inspect-export` exits 0 even when a file's row count or checksum does not match. The verdict is only the JSON `"valid"` field (`cli.py:199-215`); it raises only on a missing file (`sources/exports/reader.py:29-30`) or a manifest that fails schema validation (`sources/exports/manifest.py:73-76`). Read the JSON, never the exit code.
- `backfill-orderbook drain` reports `"stopped": "drained"` and exits 0 even when every batch found zero orders: missing uids are data, never failures (`services/backfill_orderbook.py:211,214-216,250` for the stop state; `:304-315` for missing uids counted as data). The sweep Job's exit code says nothing about coverage.
- The health server exists only inside `continuous` (`services/continuous.py:94-95`); `drain`, `backfill` and `repair` expose no `/metrics`. `/ready` is `SELECT 1` (`observability.py:103-107`, `storage/clickhouse.py:269-275`) and cannot tell whether any chain is advancing.
- `cow_chain_lag_blocks` is set only on the scan path (`services/historical.py:57,107,115`) and is legitimately enormous during catch-up; the alerting stack has no lag rule — only a commented-out template to add once each chain is near the tip (the deployments repo's `alerting/alerts/cow-indexer.yaml:4-7,88-103`), matching README's advice (`README.md:297`).
- `indexing_ranges` is written with an async ack (not in `SYNC_INSERT_TABLES`, `storage/clickhouse.py:156`), so holes in it are not unscanned blocks. `chain_blocks` is sparse by design on the forward scan (`store_all_blocks=False` keeps the range-end block plus blocks that had logs, `services/historical.py:83`).
- `auctions` and `quotes` are created by the migrations (`migrations/005_competitions.sql:1-13`, `migrations/006_metadata.sql:39-56`) but the RPC/API path never writes them; only `import-export` datasets do (`storage/clickhouse.py:1354-1355`). Empty is normal. `runs` (`migrations/001_indexing_state.sql:77-89`) is created by the schema and written by NOTHING — no `_insert("runs", ...)` exists under `src/` and no export dataset maps to it (`sources/exports/adapters.py:18-27`). It is not a run ledger; do not query it for job history.
- README's `--verify-checksums` example (`README.md:243-246`) is already the default; `--no-verify-checksums` is the flag that changes behaviour (`cli.py:221-223`).
- `README.md:159` says "run only one enrichment worker replica"; the code has no lock — `lease_work` is a `SELECT ... FINAL` then an insert (`storage/clickhouse.py:999-1049`), so two workers can lease the same items.
- The retention DELETE no longer forces `lightweight_delete_mode` (`storage/clickhouse.py:64-83`); README's `OPTIMIZE TABLE ... work_items FINAL` (`README.md:217`) is still the Code 241 unblock, but re-adding the forced mode silently disables retention with Code 344.

## Hazards

- A second `continuous` for any chain, or `backfill` beside it → double scan on one checkpoint key and duplicate leases on `work_items` → one continuous replica only; `repair` for ranges. Runbook "Safe stop and restart".
- Running the image with no args → the default CMD starts `continuous --chain all` (`Dockerfile:20`), a second writer on every chain → always pass a subcommand; one-shot Jobs copy the sweep's template.
- Deleting or rewinding `indexing_checkpoints` → the chain restarts at its pinned `from_block` (`services/historical.py:54`) and rescans years, and the `*_canonical` views, bounded to the checkpoint (`migrations/008_committed_views.sql:28-34`), hide rows meanwhile → `repair --chain X --from-block A --to-block B`. Runbook "Detect and repair".
- `purge-work` while the writer is up → two DELETE mutations race the single unpartitioned `work_items` → writer at zero replicas and `COW_PURGE_ENABLED=false` first, by a human. Runbook "purge-work".
- Any drain while the CoW edge answers 403 → each failed item burns one of `COW_MAX_ATTEMPTS`; the last writes `dead` at `MAX_REVISION-1` (`storage/clickhouse.py:1111-1113`), which a revision-0 re-seed can never overwrite → gate on `preflight` and on `cow_api_requests_total{status="403"}` staying flat.
- `seed-orders` without `--limit` → seeds every missing uid, including the pre-2022-Q3 epoch the API no longer serves (tens of thousands of uids per big chain), and adds a `uniqExact` count (`services/backfill_orderbook.py:172-175`). The whole-chain anti-join runs either way (default cap 2 GiB, `storage/clickhouse.py:240`) → always `--limit N` (production 2000), and always `CLICKHOUSE_FINAL_MEMORY_MB=6144` on the seed process only. Runbook "Orderbook history".
- A hand-started drain inside the sweep window → two drains lease the same items; `Forbid` cannot see a Job it did not create → wait for the slot, or a human suspends the CronJob first.
- A drain exec'd inside the live pod → shares its 1 GiB limit and OOM-evicts the writer → a separate Job on the sweep's template.
- A one-shot cloned from the sweep template inherits `command = ["sh","-c"]` with ONE args string (stack `cronjob.tf:88-93`), `CLICKHOUSE_FINAL_MEMORY_MB=6144` (`:117-120`), `backoffLimit 1` + `restartPolicy Never` and a 24 h TTL (`:49-50,61`) → replace that args string with the single `cow-indexer <subcommand> ...` line (bare subcommand tokens under `sh -c` fail as "not found"); drop `CLICKHOUSE_FINAL_MEMORY_MB` unless running `seed-orders` (or `drain`, which production runs with it) — it lifts every FINAL read's cap from the 1024 MiB default (`config.py:154`, `storage/clickhouse.py:231-234`).
- A hand-run `seed-owners` → one item per distinct trader (all of them without `--limit`, `storage/clickhouse.py:1527-1547`), each up to 20 pages (`config.py:203`); the next sweep's drain has no `--run-seconds` (stack `cronjob.tf:92`) and runs until neither backfill kind has an open item (`services/backfill_orderbook.py:219-220,239-245`), so it runs for hours and, under `Forbid` + `startingDeadlineSeconds 1800` (`cronjob.tf:36-37`), later slots are skipped and the 1 h–24 h leak stays open → a human decision first, and always `--limit`.
- Pinning an image whose migration is unapplied → `continuous` never migrates; every dependent work item fails and that loop backs off → run `migrate` with the new image first; `applied` must be non-empty.
- Hand-editing `work_items` to "clear a lease" → `attempts` is the retry budget; a batch abandoned at its deadline is already released without a charge (`services/enrichment.py:101-105`), and a lease lapsed by a kill is re-leased on its own after 5 min (`storage/clickhouse.py:1042`) → leave it.
- `tests/integration` or `make test` with `COW_RUN_INTEGRATION=1` exported, `make migrate|backfill|continuous`, `docker compose up`, or README's "Start over / wipe" `TRUNCATE` (`README.md:221`) with production `CLICKHOUSE_*` (`Makefile:6-19`) → migrations, inserts, a second writer or data loss in `cow_db` → never export production credentials into a shell running this repo.
- Re-adding `lightweight_delete_mode='lightweight_update_force'` to `PURGE_DELETE_SETTINGS` → every sweep fails with Code 344 and deletes nothing while the pod stays green (`storage/clickhouse.py:64-83`).

## Health and verification is a warehouse query

Liveness and freshness per chain, never summed — the query the docs page and runbook carry, over `indexing_checkpoints` (`migrations/001_indexing_state.sql:14-24`):

```sql
SELECT chain_id, argMax(block_number, updated_at) AS checkpoint_block,
       dateDiff('minute', max(updated_at), now()) AS lag_min
FROM cow_db.indexing_checkpoints WHERE source = 'rpc'
GROUP BY chain_id ORDER BY lag_min DESC;
```

Healthy: `lag_min` ≤ ~6 min on every chain whose RPC works, each chain on its own (the morning check's value, private `runbooks/00-morning-check.md:41`). Reason: the scan loop runs every 12 s and checkpoints the range-end block whether or not
the range had logs (`services/historical.py:83,96-97`, `services/continuous.py:118-120,214`), so checkpoint age measures scan liveness independently of trade volume.
Hours means that chain's RPC or scan loop is dead, even behind a green pod (verified 2026-09-22: one chain frozen six weeks, pod green). Enrichment is a separate lane
with its own freshness: `SELECT chain_id, max(creation_date) FROM cow_db.orders WHERE source != 'backfill' GROUP BY chain_id` — `creation_date` froze for weeks while
`observed_at` stayed seconds-fresh because the first API call of every batch was failing. The coverage/gap query is the sweep's anti-join (`storage/clickhouse.py:1489-1497`)
restricted to the 1 h–24 h leak band that the sweep exists to close (the band comes from the deployments stack's sweep notes, not from code); scope it to ONE chain:

```sql
SELECT count() AS traded_uids_missing_orders
FROM (SELECT order_uid, max(block_timestamp) AS last_fill FROM cow_db.trades
      WHERE environment = '⟨production|testnet⟩' AND chain_id = ⟨chain_id⟩
        AND order_uid NOT IN (SELECT order_uid FROM cow_db.orders
                              WHERE environment = '⟨production|testnet⟩' AND chain_id = ⟨chain_id⟩)
      GROUP BY order_uid)
WHERE last_fill BETWEEN now() - INTERVAL 24 HOUR AND now() - INTERVAL 1 HOUR;
```

Healthy: about 0 right after a sweep slot, low hundreds between. Never widen past ~7 days: older is the epoch the API no longer serves, a permanent residue. Sepolia is `testnet`.

NOT a health signal: pod `Running` or `/ready` 200 (only `SELECT 1`); a Job exit code of 0 (drain semantics above); `cow_rows_written_total` summed across chains (one
dead chain hides behind ten live ones); `cow_chain_lag_blocks` during catch-up; `observed_at` freshness on `orders`; row counts or holes in `indexing_ranges` /
`chain_blocks`; frontier minutes alone on low-volume chains (zero missing uids in every band is "no new orders", not a stall); any Prometheus rate in the first minutes
after a restart. Never aggregate `trades_canonical` unscoped — the block-hash join hits the per-query memory limit; read `indexing_checkpoints` instead.

## Rules for agents

- Derive from the code, never from README prose, the runbook, or the numbers in this file; re-verify the cited `path:line` before acting. Where they disagree, the code wins and you say so.
- Local tooling is not production. `Makefile`, `docker-compose.yml`, `.env` and `uv run` exist for a laptop; production is the image entrypoint with the args in the deployments stack.
- Never run a writer (`continuous`, `backfill`, `purge-work`, `import-export`, `migrate`, `tests/integration`, `make migrate|backfill|continuous`, `make test` with `COW_RUN_INTEGRATION=1`, `docker compose up`) against the production warehouse from a laptop. Read-only commands (`status`, `coverage`, `preflight`, `inspect-export`, `validate-export`, `backfill-orderbook probe|status`) are the ceiling.
- Never assume access to the cluster or the private deployments repository. Propose exact commands for a human to run. Never run a git write, a Terraform apply, a cluster-mutating command or an image push yourself; read-only plans and read-only cluster reads are fine where you already have access.
- Never a second writer; never more than one replica; never `backfill` beside `continuous` on the same chain; never a hand-started drain in the sweep window or inside the live pod.
- Never seed without `--limit`; never drain while the edge is returning 403; never rewind checkpoints; never hand-edit `work_items`; never `TRUNCATE`; never re-force `lightweight_delete_mode`.
- A schema change is a new numbered file under `migrations/`, applied by a `migrate` run with the new image BEFORE the Deployment is pinned to that image. Never edit an applied migration.
- Keep `impersonate="chrome"` in `sources/http.py:40` and the partner-gateway base URLs in `config/chains.yaml:18-106`: the edge screens on TLS fingerprint and only the gateway honours `X-API-Key`. A plain `curl`/`urllib` probe is not representative of what the app sees.
- Measure with windows, never single samples, and never in the first minutes after a restart. Count 403s with `cow_api_requests_total{status="403"}`, not a log grep (block numbers contain "403").
- Instrument first, then one change per deploy cycle (`cow_request_seconds{source="clickhouse"|"limiter"}`, `cow_enrich_*`, `cow_purge_sweeps_total`). Batch, concurrency and interval were each tuned before and none moved the per-item cost; the queue grows with discovery fan-out (`services/enrichment.py:249-277`), not retention.
- Lessons: this repo has no `.agents/` or `docs/lessons/` convention. Durable operational lessons go to the private runbook below; code-facing facts go as dated comments beside the code they constrain, which is this repo's existing practice (`storage/clickhouse.py:59-95,140-156`, `config.py:106-142`).
